# Грабли и шейдеры

Требования к камере, справочник частых ошибок, какие материалы/шейдеры поддерживаются, полное
подключение к Shader Graph.

## Камера: почему RenderMeshIndirect рисует "лишний раз"

Это отдельный раздел, потому что на нём легко потерять половину FPS и не понять почему.

`RenderParams.camera` по умолчанию `null`. Документация Unity прямым текстом:

> If set to `null` (default) renders for all cameras.

То есть если камеру не указать явно, `Graphics.RenderMeshIndirect` рисует **на каждую активную
камеру, которая рендерится в этом кадре** — не только на "основную" камеру игры. В редакторе это
означает: пока открыта вкладка **Scene**, у неё тоже есть своя камера, и она тоже получает этот
draw call, отдельно от Game view. Итог — вся сцена с кубами рисуется дважды за кадр только из-за
того, что у вас на экране одновременно Scene и Game — совершенно независимо от размера сцены или
качества кода.

Отсюда правило: **всегда явно указывать `RenderParams.camera`**, если рендер не должен быть виден
одновременно в нескольких местах. В `IndirectMeshRenderer` для этого есть поле `_targetCamera`
(по умолчанию берётся `Camera.main` в `OnEnable`, если не назначено вручную):

```csharp
var rparams = new RenderParams(_material)
{
    ...
    camera = _targetCamera
};
```

Если резкая просадка FPS появляется именно в редакторе, а в билде её нет (или наоборот, есть
несколько активных `Camera` в сцене одновременно — сплитскрин, миникарта, камера для отражений) —
проверяйте именно это в первую очередь, до всего остального в этом документе.

## Известные грабли

- **Camera = null рисует на все камеры.** См. раздел выше — самая частая причина "необъяснимой"
  просадки FPS именно при работе в редакторе.
- **Bounds всегда приблизительные.** `Graphics.RenderMeshIndirect` не может сам вычислить
  bounding box — он не знает реальных данных в буфере (это можно посчитать только на GPU, а bounds
  для culling нужны CPU-стороне заранее, до отрисовки). Поэтому `RenderParams.worldBounds` задаётся
  руками с запасом. Если объекты пропадают при повороте камеры — bounds занижены.
- **Диспоз буферов обязателен.** `GraphicsBuffer` управляет нативной GPU-памятью, GC её не
  освобождает. `OnDisable` должен звать `Dispose()`, иначе на каждый Play/Stop в редакторе будет
  утечка (в редакторе это особенно заметно — Unity явно предупредит в консоли о неосвобождённых
  нативных ресурсах).
- **Material без шейдера = исключение молча позже.** Если `Shader.Find("Custom/IndirectCube")`
  не находит шейдер (опечатка в имени, ошибка компиляции шейдера), `new Material(null)` бросит
  исключение прямо в `OnEnable` — это самый частый первый запуск с ошибкой у новичков в этой теме.
- **Порядок полей в C#-структуре обязан совпадать с HLSL.** См. [Instance-буфер](02-architecture.html#1-instance-буфер-graphicsbuffertargetstructured).
- **Culling по умолчанию выключен.** Без `_useComputeCulling` рисуются буквально все
  `_instanceCount` инстансов каждый кадр, независимо от того, видны они камере или нет. Реальный
  ComputeShader-culling в проекте есть, но включается явно — см. [GPU-culling](03-culling.html).
- **Забыли переключить буфер в шейдере при включении culling'а.** Если пишете свой culling с нуля
  по образцу этого — не забудьте, что после фильтрации шейдер отрисовки должен читать буфер
  выживших, а не исходный (см. [Критически важный нюанс](03-culling.html#критически-важный-нюанс-чей-буфер-читает-шейдер-рендера)).
  Иначе на экране окажутся не те инстансы, что реально прошли отбраковку.
- **Отсутствует ShadowCaster pass в шейдере.** `IndirectCube.shader` определяет только
  `LightMode = UniversalForward`. Даже с `shadowCastingMode = ShadowCastingMode.On` на `RenderParams`
  объект не отбрасывает тень — URP просто пропускает shadow-pass для шейдера, в котором нет
  подходящего pass'а, без ошибок и без затрат производительности. Это не баг, а недоделанная
  часть демо — тени пока не являются целью.
- **`namespace` в reflected-HLSL ломает компиляцию под Vulkan.** Официальный пример Unity для
  Shader Function Reflection API оборачивает функции в `namespace { ... }`. На Linux/Vulkan это
  падает с ошибкой `glslang: '::' not supported` / `compilation terminated` — glslang (HLSL-фронтенд
  для Vulkan) не умеет в C++-style `::`, в отличие от DXC (D3D12). Поэтому `IndirectInstancing.hlsl`
  сейчас без namespace, а имена (`IndirectCubeInstanceData`, `IndirectCubeRotateByQuaternion`)
  сделаны достаточно уникальными руками, чтобы не пересекаться с другими файлами.
- **glslang не любит несколько `return` с объявлением переменной после первого из них.** В HLSL-
  функциях `IndirectCulling.compute` это давало предупреждение "use of potentially uninitialized
  variable" под Vulkan (DXC для D3D12 не жаловался — только glslang). Не косметика: часть путей
  выполнения реально могла читать непроинициализированный регистр. Лечится переписыванием в
  однопроходном стиле: посчитать все булевы условия безусловно, объединить через `&&`, один `return`
  в конце.
- **Margin/radius должен применяться и к "объект перед камерой" проверке, не только к
  X/Y/Z-границам.** Если тест сначала проверяет `clipPos.w > 0` (сырое, без запаса), а уже потом
  добавляет `radius` к `w` для остальных осей — крупный объект мгновенно и полностью пропадает в
  момент, когда его **пивот** (не вся геометрия) пересекает плоскость камеры. Правильно — сравнивать
  с уже расширенным `w = clipPos.w + radius` на ВСЕХ этапах теста одинаково (см.
  [Тест 2: frustum culling](03-culling.html#тест-2-frustum-culling)).
- **`GL.GetGPUProjectionMatrix` нужен КАЖДЫЙ раз, когда строите view-projection матрицу для ручного
  чтения clip space/depth-буфера** — не только в одном месте файла. Если в одном месте матрица
  строится с коррекцией, а в другом — без, обе матрицы формально валидны сами по себе, но описывают
  РАЗНЫЕ конвенции clip space, и совместное использование их чисел (например, сравнение с реальным
  депсом) станет тихо неверным на конкретной платформе.
- **Поля-override, которые читаются реже, чем меняются в инспекторе.** Если закэшировать
  override-поле в обычное приватное поле один раз при `OnEnable` (а не пересчитывать каждый кадр из
  сериализованных полей), правки в инспекторе во время Play mode будут молча игнорироваться реальной
  логикой, даже если какой-нибудь диагностический гизмо (пересчитывающий их живьём отдельно) создаёт
  иллюзию, что всё применяется. При живой донастройке значений в инспекторе всегда перепроверяйте,
  ГДЕ именно поле реально читается.

## Какие материалы/шейдеры поддерживаются

Важно различать два уровня "поддержки":

**Уровень API.** `Graphics.RenderMeshIndirect` абсолютно всеяден — ему всё равно, какой шейдер
у материала. Он просто issue'ит draw call с указанным мешем/материалом/буфером аргументов. Вы
можете передать туда хоть стандартный URP/Lit материал без единой правки — компиляция и вызов
пройдут без единой ошибки.

**Уровень результата.** Но чтобы каждый инстанс оказался на своей позиции/повороте/масштабе,
**шейдер обязан сам прочитать `_InstanceBuffer` по `SV_InstanceID`** — это не происходит
автоматически. Обычный URP/Lit материал ничего не знает про наш буфер и про то, что рисуется через
`RenderMeshIndirect`, а не через `Transform`. Результат — все `_instanceCount` копий меша
отрисуются ровно в одном месте (там, куда их поставит `unity_ObjectToWorld` по умолчанию, т.е.
фактически в мировом нуле), наложенные друг на друга.

Отсюда практическое правило: **для этой техники нужен либо шейдер, написанный вручную под неё
(как `IndirectCube.shader`), либо Shader Graph с явно добавленной нодой чтения буфера** — третьего
не дано. Обычные PBR-материалы (Lit/Complex Lit/из ассет-стора) не подходят, пока в них не
встроена эта логика.

Что не имеет значения для этой техники:
- **Opaque/Transparent** — работает с обоими, `RenderMeshIndirect` не завязан на Queue.
- **Forward+ или другой render path** — этот механизм не зависит от SRP Batcher, GPU Resident
  Drawer или Batch Renderer Group, поэтому работает одинаково независимо от того, что происходит
  с остальной сценой.
- **DOTS Instancing / "Enable GPU Instancing"** — оба этих механизма тут не участвуют и не мешают
  (см. [Путь одного инстанса](02-architecture.html#путь-одного-инстанса-от-буфера-до-пикселя)) — они
  решают другую задачу (per-instance-свойства из ограниченного набора, а не произвольный буфер).

Что стоит держать в голове:
- **Прозрачность внутри одного indirect-вызова не сортируется по инстансам.** GPU рисует все
  инстансы одного draw call'а в порядке из буфера, а не по глубине. Для непрозрачных объектов это не
  играет роли (Z-buffer сам разберётся), но для полупрозрачных материалов наложенные друг на друга
  инстансы могут отрисоваться в неправильном порядке.

## Как подключить это к Shader Graph

Раньше единственным способом прочитать буфер внутри Shader Graph был Custom Function Node —
неудобная нода, где HLSL-код вставляется строкой прямо в инспектор. В Unity 6.5 появился
**Shader Function Reflection API**: пишете обычный `.hlsl`-файл с функцией, помеченной
`UNITY_EXPORT_REFLECTION`, — и Shader Graph сам находит её и рисует настоящую ноду с портами,
основанными на сигнатуре функции. Никакого копипаста HLSL в инспектор ноды.

Для этой механики уже написан `IndirectInstancing.hlsl` (лежит рядом, в той же папке) — та же
математика, что в `IndirectCube.shader`, но оформленная как reflected-функция.

### Шаги в редакторе

1. **Создайте Shader Graph** (URP Lit или Unlit — не важно): ПКМ в Project → `Create` →
   `Shader Graph` → `URP` → `Lit Shader Graph` (или `Unlit`).
2. Откройте граф. Unity уже должен был подхватить `IndirectInstancing.hlsl` и зарегистрировать
   ноду `Apply Instance Transform` в категории `Custom/Indirect Rendering` (если файл сохранён
   после того, как редактор открыт — reflection hot-reload'ится, перезапуск не нужен).
3. Добавьте ноду **`Instance ID`** (Create Node → поиск "Instance ID", категория Input/Geometry).
4. Добавьте ноду **`Apply Instance Transform`** (поиск по названию или по категории
   `Custom/Indirect Rendering`). У неё будут порты:
   - `positionOS`, `normalOS` — уже предзаполнены значениями Object Space Position/Normal
     благодаря хинтам `<Position/>`/`<Normal/>` в `.hlsl`-файле, руками подключать не обязательно
     (но можно, если нужно что-то другое).
   - `instanceID` — сюда подключите выход ноды `Instance ID`.
   - `positionWS`, `normalWS` — выходы, которые нужно протянуть дальше.
5. В Master Stack откройте вершинный контекст (**Vertex**) и подключите `positionWS` в блок
   **Position**, `normalWS` — в блок **Normal** (если блок Normal не отображается в Vertex-контексте,
   включите его через шестерёнку настроек Master Stack — в некоторых версиях URP-таргета он скрыт
   по умолчанию).
6. Сохраните граф, создайте на его основе `Material`, назначьте его в поле `_material` компонента
   `IndirectMeshRenderer`.

### Почему буфер не появится в Blackboard — и почему это нормально

Blackboard — это панель слева в окне Shader Graph, куда добавляют параметры материала (цвет,
текстуру, число), которые потом видно и можно менять в инспекторе на самом Material asset. Раз
шейдер использует какой-то буфер с данными — логично ожидать, что он тоже появится там, как
параметр, который можно найти и потрогать.

**Он там не появится. Это ожидаемо, не баг и ничего чинить не надо.**

Причина простая: у Blackboard в принципе нет типа параметра "буфер данных". Она умеет только числа,
векторы, цвета, текстуры, булевы значения — и всё. Буферов там нет и не может быть, вне зависимости
от того, что вы делаете.

Буфер в этой механике живёт не в графе, а в обычном текстовом файле `IndirectInstancing.hlsl` —
там прямо написано:

```hlsl
StructuredBuffer<InstanceData> _InstanceBuffer;
```

Это ровно то же самое объявление переменной, что раньше было в написанном руками
`IndirectCube.shader`. Shader Graph просто вставляет содержимое этого файла в итоговый шейдер как
есть, целиком — он не пытается разобрать, что внутри, кроме одной конкретной функции, которую мы
пометили для рефлексии (`ApplyInstanceTransform`). Всё остальное в файле, включая объявление
буфера, доходит до итогового шейдера "как есть", в обход графа и Blackboard.

**Что это значит на практике:** ничего не меняется в C#-коде. Строчка в `IndirectMeshRenderer.cs`,
которая кладёт данные в буфер —

```csharp
_propertyBlock.SetBuffer(InstanceBufferId, _instances.Buffer);
```

— продолжает работать один в один что для шейдера, написанного руками, что для шейдера, собранного
через Shader Graph. Вам не нужно ничего "выставлять" или "находить" для этого буфера в самом
графе — там его просто не будет, и это правильно.
