Диагностика: как искать баги culling'а

Три теста, GPU-параллелизм и матрицы camera-space — комбинация, в которой "просто посмотреть на экран" почти никогда не говорит, какой из трёх тестов и почему отбросил конкретный объект. Поэтому на компоненте есть отдельный набор диагностических полей — они не влияют на сам culling (кроме _invertOcclusion, который специально для этого и существует), только показывают, что происходит.

_debugInstanceIndex — построчный разбор ОДНОГО инстанса

Задайте индекс инстанса (0.._instanceCount-1) — раз в секунду в консоль печатаются три строки:

  1. Сырые числа frustum-теста: clipPos.xyz, w(+radius) — те же величины, что участвуют в IsInsideFrustum, чтобы видеть реальные значения, а не гадать по картинке.
  2. Occlusion — числа для центра инстанса: uv (где в depth-текстуре прошлого кадра ищем), sceneDepth/instanceDepth (что сравнивается), withinPrevFrame, occludedByDepth.
  3. Occlusion — 7-точечная маска: occludedCount/7 и битовая маска, какие именно из 7 точек (центр, +Y, -Y, +X, -X, +Z, -Z) сейчас считаются скрытыми. Инстанс реально отбрасывается только при occludedCount = 7. Что такое эта маска и как её читать — ниже.

Если включён LOD (см. LOD), эти три строки печатаются один раз за кадр и отражают данные ПОСЛЕДНЕГО LOD-бакета, обработанного в этом кадре — не всех сразу.

_debugShowAllFrustumStatus — визуальный обзор всех инстансов сразу

Индекс конкретного "виновника" среди тысячи инстансов на глаз не найти. Эта галочка рисует в Scene view маленькую сферу на каждом инстансе — зелёную, если CPU-копия frustum-теста (IsInsideFrustumCpu, та же формула, что в compute shader'е, пересчитывается каждый gizmo-кадр живьём) считает его видимым, красную иначе. У красных сфер рядом всплывает подпись с индексом инстанса — только у красных, иначе тысяча подписей друг на друге нечитаема.

Практический workflow, чтобы найти конкретный баг:

  1. Включите _debugShowAllFrustumStatus на нужном рендерере во время Play mode.
  2. Дождитесь/спровоцируйте момент, когда объект, который вы видите на экране, пропадает.
  3. Найдите его красную сферу в Scene view, прочитайте подпись-индекс рядом с ней.
  4. Подставьте этот индекс в _debugInstanceIndex — получите три строки точных чисел именно для этого инстанса, не для случайного.

Если сфера зелёная (frustum говорит "видим"), а объект всё равно не рисуется — дело не во frustum, смотрите на occlusion-числа из _debugInstanceIndex (или временно выключите _enableOcclusionCulling, чтобы проверить гипотезу изоляцией).

Важно: живое vs закэшированное значение radius/extents

_boundsRadiusOverride/_boundsExtentsOverride пересчитываются в актуальный радиус/extents каждый кадр, заново, локальными переменными — и в DispatchAndRenderWithCulling() (для реального GPU-теста), и отдельно в OnDrawGizmos() (для визуализации), — ни то, ни другое нигде не кэшируется между кадрами. Раньше было не так (значение кэшировалось один раз при OnEnable в поле): правка override-поля в инспекторе во время Play mode визуально меняла гизмо, но реальный GPU-тест продолжал молча работать со старым значением, что давало ложные выводы при отладке ("тест же зелёный, почему объект всё равно пропал?"). Сейчас оба места читают одно и то же живое значение из инспектора каждый раз заново — гизмо и GPU-культинг больше не могут разойтись из-за этого.

Как работать с битами

_DebugOccludedMask (и вообще любая битовая маска в коде) — это способ упаковать несколько да/нет-флагов в одно целое число, вместо массива из 7 отдельных bool. Если вы не работали с этим раньше — вот как это устроено, на примере реального кода из этого проекта.

Что такое бит

Число в компьютере хранится в двоичной системе — как последовательность нулей и единиц (бит — одна такая цифра, 0 или 1). uint (беззнаковое целое) в HLSL/C# — это 32 бита подряд. Нам из них нужно всего 7 (по одному на каждую из 7 точек occlusion-теста), но принцип не зависит от того, сколько битов реально используется.

Число 13 в двоичной записи — 00001101 (считая справа налево: бит 0 = 1, бит 1 = 0, бит 2 = 1, бит 3 = 1, остальные — 0). Каждый бит — это ОТДЕЛЬНЫЙ независимый флаг "да/нет" внутри одного числа.

Три оператора, которые реально использует код

uint occludedMaskDbg = 0;
for (int j = 0; j < 7; j++)
{
    float3 samplePosDbg = inst.position + RotateByQuaternion(offsetsDbg[j], inst.rotation);
    if (IsPointOccluded(samplePosDbg)) occludedMaskDbg |= (1u << j);
}

1u << j (сдвиг влево, <<) — берёт число 1 и сдвигает его биты влево на j позиций. 1u << 0 = 00000001 (бит 0 включён), 1u << 3 = 00001000 (бит 3 включён), и так далее. Это способ получить "число, у которого включён ровно один конкретный бит номер j, а все остальные — 0".

|= (побитовое ИЛИ с присваиванием, |) — включает бит, не трогая остальные, уже включённые биты. mask |= (1u << j) значит "поставь бит номер j в 1 в mask, оставь все остальные биты как были". Если бы вместо |= использовалось простое =, каждая новая точка СТИРАЛА бы результат всех предыдущих точек — |= этого не делает, он именно ДОБАВЛЯЕТ бит к уже накопленным.

& (побитовое И, AND) — используется при ЧТЕНИИ маски обратно, проверить, включён ли конкретный бит:

for (int bit = 0; bit < 7; bit++)
    if ((mask & (1u << bit)) != 0) occludedCount++;

mask & (1u << bit) даёт ненулевой результат, только если И в mask, И в (1u << bit) этот конкретный бит равен 1 одновременно — то есть это буквально вопрос "включён ли бит номер bit в mask?". Раз (1u << bit) — это число с единственным включённым битом, & с ним "вырезает" из mask ровно один этот бит, игнорируя все остальные.

Пример с реальными числами

Допустим, у инстанса скрыты точки с индексами 0 (центр), 2 (-Y) и 5 (+Z), а остальные 4 видны. После цикла mask будет равен (1u<<0) | (1u<<2) | (1u<<5) = 1 + 4 + 32 = 37, в двоичном виде 0100101 (читая справа налево: биты 0, 2, 5 включены, остальные — нет). Именно поэтому лог диагностики печатает маску через Convert.ToString((int)mask, 2) — переводит число в текстовую строку из нулей и единиц, чтобы можно было увидеть, какие ИМЕННО точки скрыты, не считая в уме.

Шпаргалка: остальные побитовые операторы

В коде этого проекта используются только <<, &, |= (см. выше) — но для полноты, вот все основные побитовые операторы C#/HLSL (одинаковый синтаксис в обоих языках), на 4-битных примерах:

  • AND (&) — результат бита 1, только если ОБА бита равны 1: 0110 & 0011 = 0010.
  • OR (|) — результат бита 1, если хотя бы один из битов равен 1: 0110 | 0011 = 0111.
  • XOR (^) — результат бита 1, если биты РАЗНЫЕ: 0110 ^ 0011 = 0101.
  • NOT (~) — переворачивает каждый бит на противоположный: ~0110 = 1001.
  • Сдвиг влево (<<) — двигает все биты влево, справа дописывает нули: 0001 << 2 = 0100.
  • Сдвиг вправо (>>) — двигает все биты вправо: 1000 >> 2 = 0010.

Практическое правило, когда это вообще имеет смысл использовать: если вам нужно упаковать МНОГО независимых да/нет-состояний экономно (в одно число вместо массива bool'ов) — как в _DebugOccludedMask — или прочитать/записать один конкретный бит, не трогая остальные — это оно. Для обычной логики "если A и B" в коде достаточно &&/|| (логическое И/ИЛИ на bool, не путать с &/| на числах — это разные операторы, просто похожие символы).
