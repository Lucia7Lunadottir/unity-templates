# Производительность

Что измерено, на что уходит время кадра и что мы для этого сделали. Все цифры - **Unity Editor, Play Mode, режим
энергосбережения процессора** (governor `powersave`, ~1 ГГц: в 3-4 раза медленнее обычного режима и с шумом ±30%),
20 000 агентов-кубов с рендером, камера с тегом `MainCamera`. Сравнивать цифры можно только внутри одного режима.
Режим питания системы мы не меняем и считаем худший случай.

## 1. Что считается где

| Задача | Где | Чем |
|---|---|---|
| Путь до цели | CPU, воркеры | `NavWorld` в `IJob` на каждом воркере |
| Высота, стены, шаг | CPU, воркеры | `NavWorld.MoveLocation` в `IJobParallelFor` |
| Прямой ход | CPU, воркеры | `NavWorld.Raycast` |
| Разведение соседей | CPU, воркеры | spatial hash + `IJobParallelFor` |
| LOD | CPU, воркеры | `IJobParallelFor` по расстоянию до камеры |
| Запись `Transform` | CPU, воркеры | `IJobParallelForTransform` |
| Рендер десятков тысяч | GPU | `RenderMeshIndirect` по `Agents`/`AgentsGpu` |

**ComputeShader в ядре:** разведение агентов (`SwarmAvoidance.compute`: uniform grid на хэш-таблице со связными списками + проход на агента,
результат через `AsyncGPUReadback`, `04-how-it-works.md`, раздел 6). Пути, высота и стены остаются на CPU: данные NavMesh для ComputeShader
напрямую не отдаются. Отрисовка и ваши ComputeShader'ы поверх `AgentsGpu` (позиция, направление, скорость, тир) - тоже GPU.
**Оговорка по измерениям:** переключение `GpuAvoidance` на моих прогонах и на 100 000 агентов в `SwarmNavDemo` не изменило FPS, то есть выигрыш по
скорости не доказан; GPU-вариант нужен прежде всего ради качества (все агенты любого тира без потолка в 24 соседа, правило прибытия).

## 2. Результаты (20 000 агентов, LOD 60/150 м, интервалы 2/4, с разведением)

Ожидание навигации - сколько главный поток ждёт джобы в `LateUpdate` (то, что навигация реально добавляет к кадру).
Целый FPS сцены для оценки навигации не годится: базовый кадр этой тестовой сцены ~41-44 мс без единого агента.

| Вариант | Ожидание навигации p50 |
|---|---|
| Первый перенос на `NavWorld` (пути на критическом пути, хэш всех агентов) | 8-10 мс |
| + LOD-интервалы 2/4 по умолчанию | 6,7-8,5 мс |
| + пути в фоне после шага, Far не в хэше | 1,6-2,3 мс |
| + сглаживание Mid/Far в кадре камеры | 1,6-1,8 мс (шум машины ±30%) |
| Погоня 20 000 за одним агентом | 2,5-3,8 мс (иногда до 5 мс на пике) |

Для справки: прежний сырой тест без разведения и без хэша (только пути, `MoveLocation`, запись `Transform`) давал 2,3-2,8 мс с LOD и
6,6-7,4 мс без LOD - то есть разведение и хэш в итоге почти бесплатны.

## 3. Замер по стадиям

`SwarmNav.ProfileStages = true` после каждой стадии ждёт её джобы и пишет время в `StageMs` (`StageNames`). Это измеряет
стоимость каждой стадии отдельно и **отключает перекрытие**, поэтому кадр с включённым замером медленнее обычного.
`SwarmCrowdStressTest` печатает стадии в строке `SWT` (поле `profileStages`).

Типичные значения на 20 000 агентов (мс, при ~19 700 идущих):

| Стадия | Время | Заметка |
|---|---|---|
| LOD + хэш | 0,2-0,7 | хэш без Far-агентов |
| Заявки (Collect) | 0,05-0,5 | `IJob`: до `PathRequestsPerFrame` агентов за кадр |
| Пути | 3,9-5,7 | 64 пути за кадр; **в фоне, не на критическом пути** |
| Направление + разведение (Steer) | 0,16-0,25 | почти всё - чтение пары массивов и хэша |
| Шаг по NavMesh (Move) | 1,3-1,5 | `MoveLocation` для шагающих в этот кадр |
| Запись `Transform` | 0,4-0,6 | пишет только изменившихся |

Пути самые дорогие, но стоят в фоне: основная цепочка (LOD, хэш, Steer, Move, запись) на критическом пути даёт ~2-3 мс.

## 4. Что сделали и почему помогло

1. **Два джоба вместо одного** (шаг и запись `Transform`): `MoveLocation` внутри `IJobParallelForTransform` в 5 раз
   медленнее, чем в `IJobParallelFor`, из-за деления работы по иерархиям `Transform`.
2. **`TransformAccessArray(desiredJobCount = 128)`**: ~30% к записи в старой схеме.
3. **LOD по времени** (Near каждый кадр, Mid/Far раз в 2/4 кадра с накоплением `dt`): основной выигрыш на шаге и записи.
4. **Пути после шага, в фоне.** Заявка этого кадра не обязана быть готова к его Steer; она готова к следующему.
5. **Far не в хэше и без разведения** (`SeparateFarAgents = false`): издалека разведение не видно, а хэш строится только по Near/Mid.
6. **Прямой ход к близкой цели** (`Raycast`): убирает пути у ближних преследователей.
7. **Поворот считаем только у сдвинувшихся**, запись `Transform` - только при изменении позиции или поворота.
8. **Сглаживание только Mid/Far в кадре**: убирает рывки без записи `Transform` всех агентов каждый кадр.

## 5. Что не помогло или не нужно

- **Целый FPS сцены** для оценки навигации не годится (шум, базовый кадр сцены 41-44 мс): смотрите ожидание навигации и p90/p99.
- **Замеры без рендера** не показывают реальный кадр: во всех цифрах выше `Renderer` у агентов включён.
- **Дальнейшее дробление джобов** не пробовали: после разделения шага и записи `Transform` остальное - на мелочах.

## 6. Узкое место - не навигация, и замеры в Editor вводят в заблуждение

**Замер без навигации.** `TransformMoveBenchmark` (рядом со скриптами) двигает только `IJobParallelForTransform` по прямой, без путей, NavMesh и SwarmNav.
На 21 000 кубов он даёт 17-20 FPS (запись Profiler выключена), а `SwarmAgent` на 20 000 - 15-18 FPS. Те же 20 000 **неподвижных** кубов - 58-63 FPS.
То есть потолок для двигающихся `GameObject` задаёт сам Unity (обработка изменений `Transform`: границы рендерера, culling), а навигация SwarmNav добавляет 1-3 мс.
Чтобы выйти за ~20 тысяч двигающихся, агенты не должны быть `GameObject` (`RenderMeshIndirect`).

**Editor и Profiler.** Включённая запись Profiler и сам Editor дают в такие замеры больше кадра, чем вся навигация (кадр 100+ мс даже на 1000 кубов при записи Profiler).
Для оценки кадра выключайте запись и окно Profiler; для абсолютных значений нужна сборка. Burst Safety Checks, Jobs Debugger и Leak Detection в Editor
замедляют джобы с массивами в разы.

**Фоновые пути и чтение `Agents`.** Раньше фоновые пути не были бесплатными: любой вызов API, трогающий данные агентов, дожидался идущих путей, и кадр ждал самый долгий из них. Теперь пути работают только со своей копией запроса (`SwarmPathRequest`/`SwarmPathResult`), и API ждёт лишь основную цепочку кадра. `Agents`, `GetAgentPosition`, `GetSteeringDirection` ждут только основную цепочку (шаг); остальное -
всё. Ограничение путей частью воркеров (`PathWorkers`) показало себя хуже: пути идут дольше, а ждать их всё равно приходится.

## 6а. Узкое место на 70 000 через VAT - тоже не навигация

На 70 000 животных через VAT с `RenderMeshIndirect` и анимацией (`VATCrowdIndirectRendererNav`) прежняя и новая
навигация дали почти одинаковый FPS (~15): там решает геометрия моделей и стоимость VAT-шейдера, а не навигация.
Навигация на 20 000 агентов - 2-4 мс из кадра в 40+ мс.

## 7. Проверка публичного API SwarmAgent

`Tests/SwarmAgentApiTest` проверяет: прибытие и `remainingDistance`, высоту относительно NavMesh с учётом `baseOffset`,
`isStopped`, `ResetPath`, `Warp`, недостижимую цель (`Partial`), агента вне NavMesh (`Invalid`), удаление соседнего агента.
Последний прогон (2026-10-07, Editor): **все 16 проверок прошли**.

| Проверка | Результат |
|---|---|
| `hasDestination`, `pathPending/Complete` сразу после `SetDestination` | OK |
| Прибытие к точке в ~60 м | за 5,8 с, остаток 0,10 м (`stoppingDistance` 0,5) |
| Высота агента относительно NavMesh с `baseOffset` | расхождение 0,000 м |
| `isStopped = true` / `false` | стоит на месте / снова идёт |
| `ResetPath` | `hasDestination = false`, агент остановился |
| `Warp` | позиция совпала (0,00 м), `isOnNavMesh` |
| Недостижимая цель (изолированная часть NavMesh) | `pathStatus = Partial`, агент дошёл до ближайшей достижимой точки (за 56,6 с, около 33 м от цели) и остановился |
| Агент вне NavMesh | `isOnNavMesh = false`, `pathStatus = Invalid`, без исключений |
| `Destroy` соседнего агента | остальные не пострадали |

Одна проверка в более раннем прогоне не прошла из-за самого теста, а не API: недостижимая цель была в ~1000 м, и агент не
успел дойти за 60 с (тест теперь берёт ближайшую); а проверка «агент остановился после `ResetPath`» зависела от
сглаживания дальних агентов (показанная позиция ещё догоняет настоящую 0,3-0,4 с).

## 8. Что не измерено

- Сборка (не Editor): все цифры из Editor.
- Нормальный (не энергосберегающий) режим процессора.
- 50 000 `GameObject` с `Transform` целиком (измерено 20 000 с `GameObject` и 70 000 без).
- Реальный большой мир (много Terrain-тайлов, стриминг NavMesh): тестовая сцена ~1 км².
- `NavMeshLink` на новом ядре: тест `Tests/SwarmLinkTest` написан, но до конца на сцене не прогонялся (прогон был прерван). Прежняя проверка связи шла на предыдущей версии ядра.
- Плавающие острова: в тестовой сцене их нет.
- GPU-разведение (ComputeShader) как альтернатива CPU: не реализовано.
