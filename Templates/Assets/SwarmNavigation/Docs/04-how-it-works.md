# Как устроено под капотом

Читайте, если `SwarmAgent` не хватает: нужен свой контроль над движением, `RenderMeshIndirect` без `GameObject` или
понять, почему агент ведёт себя так. Сначала краткая картина, потом по частям.

## 1. Что хранится

`SwarmNav` держит данные агентов в **параллельных массивах** (индекс = слот агента), а не в объектах: Burst-джоб
читает такие массивы подряд, без указателей и сборки мусора.

| Массив | Тип | Что в нём |
|---|---|---|
| `Agents` | `SwarmAgentState` | **Публичное** состояние: `Position` (на NavMesh), `Velocity` (направление шага, длина 0..1), `Speed`, `Tier`, `Generation` |
| `_nav` | `SwarmAgentNav` | Внутреннее состояние: привязка `NavLocation Loc`, цель, `State`, статус пути, углы, прыжок по связи |
| `_corners` | `float3` | `MaxCorners` (24) углов пути на агента: слот `i * 24 ..` |
| `_steps` | `SwarmStep` | Результат `SteerJob` для `MoveJob`: направление шага и накопленное `dt` |
| `_groupGoalPos/_groupGoalLoc` | `float3` / `NavLocation` | Общие цели (погоня): позиция и её привязка к NavMesh |

**Хэндл** `SwarmNavHandle` = слот + `Generation`. При `UnregisterAgent` поколение растёт, и старый хэндл тихо
перестаёт быть валидным, а не читает данные нового агента в том же слоте. Свободные слоты - «призраки» с позицией
`(1e6, 0, 1e6)`, чтобы не попадать в хэш рядом с живыми.

`SwarmAgentNav.State`: `Idle` (нет пути или дошёл), `Requested` (ждёт расчёта), `Following` (идёт по углам).

## 2. Кадр SwarmNav

`ScheduleTick(dt)` ставит цепочку джобов; каждый получает хэндл предыдущего (зависимости), поэтому порядок гарантирован,
а независимые друг от друга джобы идут параллельно.

```
Tier (LOD) -> [Hash, CPU-режим] -> Steer -> Move -> Pack -> [WriteTransforms]   основная цепочка, ждёт LateUpdate
                                                   \-> Collect -> Paths x N     фон, ждёт следующий ScheduleTick
Complete(): упакованные позиции -> GPU (3 диспатча) -> AsyncGPUReadback -> Poll() -> Steer следующих кадров
```

1. **LOD (`TierJob`).** По расстоянию до фокуса камеры пишет `Tier` каждому агенту. Свободные слоты всегда Far;
   без фокус-точки живые агенты - Near.
2. **Hash (`BuildHashJob`, только CPU-режим).** Позиции агентов -> `NativeParallelMultiHashMap` по ячейкам размером `2 * AvoidanceRadius`.
   Far-агенты в хэш не попадают (`SeparateFarAgents = false`). В GPU-режиме (по умолчанию) этой стадии нет: разведение считает ComputeShader (раздел 6).
3. **Steer (`SwarmSteerJob`, `IJobParallelFor`).** Для каждого агента с целью решает, куда идти: прямо (раздел 5), по
   углам пути (раздел 4), прыжок по связи или прибытие; затем добавляет разведение с соседями (раздел 6).
   Пишет только `Steps[i]` и свой `_nav[i]`.
4. **Move (`SwarmMoveJob`).** Делает шаг: `NavWorld.MoveLocation(loc, следующая точка)` возвращает новую привязку к
   NavMesh; её `position` - новая позиция агента, **с высотой поверхности**. Стены учитываются: `MoveLocation` не выходит
   за границу NavMesh.
5. **Pack (GPU-режим).** `SwarmPackAgentsJob` пакует позиции и флаги для GPU.
6. **Collect + Paths (после Move, в фоне).** `CollectRequestsJob` выбирает до `PathRequestsPerFrame` агентов, которым
   нужен путь; `PathJob` на каждом воркере (по `NavQueryBuffer` на воркер) считает им пути.

Почему пути идут **после** шага: агенту, получившему цель в этом кадре, всё равно нужен путь, а ждать его на
критическом пути кадра нет смысла. Выбор заявок (`Collect`) входит в основную цепочку и копирует всё нужное в запрос
(`SwarmPathRequest`: позиция, привязка, цель, номер `Serial`, `Generation`). Сам `PathJob` читает только запрос и пишет только результат
(`SwarmPathResult`) и углы в общий массив `Corners`, поэтому вызовы API (которые пишут `Nav`/`Agents`) пути не ждут. В начале следующего
кадра `SwarmMergePathsJob` переносит результаты в состояние агентов; результат отбрасывается, если агента удалили (`Generation`) или его цель/позиция менялись
после запроса (`Serial` растёт при `SetDestination`, `ResetPath`, `Warp`). На замере 20 000 агентов это убрало 1-5 мс с критического пути (раздел 7 в
`07-performance.md`).

## 3. Синхронизация и безопасность данных

Джобы владеют массивами, пока работают. Любой метод `SwarmNav`, который трогает данные агента из главного потока, вызывает
`Sync()`: дожидается основной цепочки и фоновых путей. Первый такой вызов за кадр после `Update` драйвера ждёт, остальные
бесплатны. `NavWorld` - read-only контейнер: все джобы регистрируются в нём через `AddDependency`, чтобы Unity не
пересобрал NavMesh, пока они читают.

## 4. Путь: NavWorld + funnel

`PathJob` для каждой заявки:

1. привязывает старт (`nav.Loc`) и цель (`MapLocation` в окне `QueryExtents`);
2. ищет путь по полигонам: `BeginFindPath` -> `ContinueFindPath` (по 512 узлов за шаг) -> `EndFindPath`;
3. читает статус из `EndFindPath`: флаг **`PartialResult` приходит именно там**, а не в статусе цикла `ContinueFindPath`.
   Он значит «цель недостижима, путь ведёт только к ближайшей достижимой точке»;
4. строит **углы** кратчайшего пути внутри коридора полигонов алгоритмом **funnel** (Simple Stupid Funnel Algorithm).

**Funnel** работает на порталах - общих рёбрах соседних полигонов пути. Для каждого портала известны левая и правая
точки. Алгоритм держит «воронку» от текущей вершины (apex) до левого и правого края и сужает её с каждым порталом; когда
новый портал выходит за воронку, последний край становится углом пути и новой вершиной. Результат - ломаная, которая
касается только углов стен и не петляет по серединам полигонов. Реализация - `SwarmFunnel.Run` в `SwarmNavJobs.cs`.

Если полигонов с `NavMeshLink` в пути несколько, участки между ними считаются отдельно: последний угол участка
отмечается в `LinkMask` как **вход в связь**, а следующий угол - выход. Углов не больше `MaxCorners` (24): если путь
длиннее, он усекается, и дойдя до последнего угла, агент просит новый путь от места, где оказался.

**Частичный путь.** Конечная точка берётся в середине последнего портала (ближайшая достижимая), `Status = Partial`.
Дойдя до неё, агент прибывает (`hasDestination` становится `false`).

## 5. Прямой ход

Если цель ближе `DirectMoveRange` (30 м), `SteerJob` делает `NavWorld.Raycast(loc, цель)`. Нет препятствия - агент идёт
напрямую к цели, путь не нужен (флаг `Direct`, пересчёт пути для него не запрашивается). Есть препятствие - обычный путь.
Потерял прямую видимость - `State = Requested` и новый путь без `RepathCooldown`. Это дёшево (замер: 20 000 лучей
~2,4 мс на одном потоке) и снимает основную нагрузку при погоне: ближние преследователи не расходуют бюджет путей.

## 6. Разведение соседей: GPU (по умолчанию) и CPU

Для каждого агента перебираются ячейки хэша 3x3 вокруг него, до `MaxNeighborsPerAgent` соседей. Для каждого ближе
`AvoidanceRadius` суммируется отталкивание, убывающее с расстоянием. Результат смешивается с направлением к углу:
`dir = normalize(flow * FlowWeight + separation * SeparationWeight)`. Потолок на число соседей нужен, чтобы стоимость
не росла как O(N²), когда толпа стягивается в одну точку: почти все агенты окажутся в нескольких ячейках, и без
потолка каждый перебирал бы всех остальных там.

**GPU-вариант** (`SwarmAvoidance.compute`, класс `SwarmAvoidanceGpu`). После основной цепочки `SwarmPackAgentsJob` пакует позиции агентов и флаги (активен, "прибыл", группа цели) в `float4`. В `Complete()` массив уходит в `GraphicsBuffer`, и три диспатча считают разведение для **всех** агентов, независимо от тира:

1. `CSClear` - обнуляет хэш-таблицу голов списков;
2. `CSBuild` - каждый агент вставляет себя в список своей ячейки (`InterlockedExchange` по `Heads[hash(ячейка)]`, `Next[i]` - прежняя голова). Без сортировки и префиксных сумм;
3. `CSSolve` - обход 3x3 ячеек (до `GpuMaxNeighbors` соседей): толчок, давление (число соседей в радиусе) и число касаний уже прибывших агентов своей группы.

Толчок содержит ещё боковую составляющую (всегда в одну сторону), чтобы агенты лоб в лоб расходились, а не замирали; от прибывшего (неподвижного) отталкивание сильнее. Результат возвращается через `AsyncGPUReadback` с задержкой 1-3 кадра: колбэк копирует его в промежуточный массив, а `Poll()` (в начале следующего `ScheduleTick`, пока джобы не идут) переносит в массив, который читает `SteerJob`. Свои `NativeArray` в API readback не передаются: он требует массивы без защиты джоб-системы. Если никто не двигался в прошлом кадре (`MovedLastFrame == 0`), диспатч пропускается.

**Правило прибытия (`ArrivalJam`).** Группа агентов идёт к одной точке, а места вокруг неё ограничены (100 000 агентов с личным пространством 1 м занимают круг радиусом около 190 м). Агент, который коснулся уже прибывшего из **своей** группы и находится не дальше радиуса, который займёт вся группа, считает цель достигнутой и встаёт: стоящие становятся неподвижными препятствиями, и диск растёт наружу. "Прибывшим" считается только тот, кто дошёл по пути (`Complete`/`Partial`); агент с недействительным путём (`Invalid`) других не останавливает.

**CPU-вариант** (если нет compute или `GpuAvoidance = false`): перебор ячеек хэша 3x3, до `MaxNeighborsPerAgent` соседей, Far-агенты в хэш не попадают.

Разведение даёт только направление шага. Шаг делает `MoveLocation`, поэтому оттолкнутый к стене агент упирается в
границу NavMesh, а не выходит за неё.

## 7. LOD по времени и Far-агенты

Near шагает каждый кадр. Mid и Far - раз в `MidUpdateEveryNFrames`/`FarUpdateEveryNFrames` кадров (фаза `(frame + index)
% N`, чтобы они не шагали все в один кадр), а пропущенное `dt` копится в `PendingDt` и применяется на следующем шаге.
Скорость движения не меняется, только частота обновления позиции.

**Far dead reckoning (`FarDeadReckoning`).** Стоимость `MoveLocation` растёт с пройденным расстоянием (он обходит полигоны), а Far шагает раз в N кадров сразу на N шагов, так что LOD сам по себе её не экономит. Поэтому Far-агент идёт вдоль углов пути на `speed * dt` без `MoveLocation`: отрезки между углами лежат на NavMesh, высота интерполируется по углам. Привязка к полигону (`NavLocation`) при этом устаревает - у агента ставится флаг `LocStale`, и перед любым использованием (шаг после выхода из Far, путь, `Move`, толчок) выполняется `MapLocation`. Far-агент не учитывает толчок соседей и идёт строго по углам. Дальше `SwarmCrowd` сглаживает это визуально
(`03-swarm-crowd.md`, раздел 5).

## 8. Прыжок по NavMeshLink

Дойдя до угла-входа, агент начинает прыжок: `Jump` растёт от 0 до 1 со скоростью `speed * LinkSpeedMultiplier / длина`,
позиция - `lerp(вход, выход, Jump)`, `MoveLocation` не используется. На `Jump >= 1` агент привязывается к полигону
выхода через `MapLocation`. Если привязка не удалась, запрашивается новый путь.
Прыжок - прямая между концами связи; дуги, анимации и обходов на нём нет.
